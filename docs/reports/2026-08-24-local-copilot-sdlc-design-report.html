1. 结论

唯一 AI

所有推理只发生在开发者本机的 VS Code Copilot Chat；服务器 MCP 和 Workflow Service 都是确定性服务。

分层工作流

Epic 编排共享结果，Ticket 管理技术栈交付，Repo Task 管理代码和 PR；三层引用同一事实，不重复分析。

人工控制

用户在 VSIX 看到下一步，并在 Copilot Chat 手动提交命令；审批、跳过、PR 和发布均保留人为决定。

重要：用户可以跳过“重复开会或重复提问”，但不能无证据跳过必需产物、风险说明和高风险审批。

2. 约束与总体架构

  • VSIX 第一版不使用 Language Model API，也不成为第二套 AI 编排器。
  • VSIX、Webhook 和服务器不能无人值守唤醒或提交 Copilot 任务。
  • Jenkins 只执行现有 Groovy/Jenkinsfile CI，不增加服务器 Agent 或模型分析。
  • MVP 使用公司 MongoDB 保存权威结构化状态和制品；HTML 按需生成，Jira 只保存摘要和可选附件；GridFS/S3 后置。
  • MVP 权限为 AUDIT_ONLY：必须登录并绑定工号，但暂不验证 TL/SM/PO 等角色。
  • Server MCP 使用逐用户身份/Token；不允许共享万能账号成为默认方案。

3. 整个流程如何触发

入口在 VSIX，但 AI 步骤由用户在 Copilot Chat 中手动启动。VSIX 负责确定性任务、状态、报告、审批和指引。

现在共有三种顶层工作流

工作流分层；PR、CI、Review、QA 和 Release 是阶段或任务，不是额外顶层工作流
工作流范围主要责任
Epic DeliveryJira Epic / Delivery Group共同业务结果、Journey、共享需求与设计、跨端依赖、兼容和发布策略、聚合状态
Ticket SDLC一个 API/Web/Android/iOS Ticket技术栈增量、批准、子 Repo Tasks 和 Ticket 完成条件
Onboarding/SyncRepo/Journey/Domain 知识基线、Freshness、依赖更新和文档 PR，不承担 Feature 交付状态

不存在冲突：Epic Delivery → Ticket SDLC → Repo Delivery Task 是父子编排。Repo Task 是 Ticket 内部针对一个仓库/PR 的子状态机，不是第四种顶层 Workflow；单仓 Ticket 自动创建并隐藏这一层。

最开始做什么

  1. 多 Ticket Epic：先在 VSIX Epic View 或 Scrum Master View 启动/加入 Epic Workflow，导入 API、Web、Android、iOS 子 Ticket。
  2. 只检查受影响 Repo/Journey 的 Onboarding Readiness；缺失/部分/过期仍可开始 Discovery，并创建定向同步任务。
  3. 在 Epic 层完成共享 Requirement Contract、跨端设计边界、依赖和发布计划，再解锁子 Ticket。
  4. 独立 Ticket：直接启动 Ticket Workflow；系统后台创建不可见的单 Ticket Delivery Group，用户无需额外操作。
  5. 如果 Ticket 已属于活动 Epic，VSIX 只提供 Join existing Epic workflow，不重复创建需求分析。
Onboarding 门禁（已选 A）：Epic 可在 MISSING/PARTIAL/STALE 开始分析；进入受影响的高风险 Design/Coding 前，关键渠道必须有验证证据，或显式记录 KNOWN_GAP 和风险接受。紧急变更可以使用有期限例外。

第一次使用

  1. 安装 VSIX，打开 SDLC Onboarding。
  2. 用 GitHub Enterprise 登录 Workflow Service；管理员完成一次工号绑定，VSIX 只展示并刷新已验证身份。
  3. 在 Customization Center 安装并激活批准的 Stable 配置包。
  4. 选择仓库 Profile：Java API、Web、iOS 或 Android。
  5. 在 Local MCP Center 安装必需 MCP，确认来源、权限和信任。
  6. 执行 Jira、GitHub、Knowledge、Figma/设备工具的只读健康检查。
  7. 打开一个仓库或多根 Workspace，运行 Repo/Journey Onboarding。
  8. 回到 My Tasks，选择 Jira Ticket 并点击 Start Workflow。

每个 Ticket 的第一步

VSIX: Start Workflow
→ 复制建议命令：/start-ticket ABC-123 --workflow WF-2026-001
→ 用户在 Copilot Chat 选择 Requirement Analyst
→ 用户粘贴并手动提交

VSIX 可以打开 Chat 和复制命令，但不自动提交。Agent 完成后通过 MCP 提交结果，VSIX 自动刷新并展示 HTML Requirement Report。

Epic 与紧急变更 Agent

/start-epic 使用只读 Epic Delivery Analyst Agent，组合 Epic Intake、Journey Gap、需求追问、跨 Ticket 依赖、API 兼容和发布编排 Skills，输出 Intake Report、Scope/Gap Map、Journey Map、Child Ticket Matrix、Source Manifest 和后续任务。它不写代码、不审批，也不替代 Solution Architect。

重大紧急变更可从 VSIX 手工创建 Epic Change Request，不覆盖已批准版本，而是生成新 Requirement Contract 候选版本并把依赖制品标记为 POSSIBLY_STALE。MVP 所有已登录用户可启动；角色标记为 UNVERIFIED_ROLE 并完整审计。

Jira 可见记录

Workflow Service 是事实源；Jira Comment 是给未使用 VSIX 的人员看的简洁投影。创建一条当前状态摘要，并只在启动、需求批准、设计批准或有证据跳过、关键阻塞、PR Ready、QA/发布完成和取消时追加里程碑评论。评论包含幂等标记、真实操作人、时间、结果、报告链接和下一步；不发布 Prompt、源码、Agent Checkpoint 或每条测试。

同步失败：先持久化 Workflow 审计事件，再异步写 Jira。失败标记 JIRA_SYNC_PENDING 并重试，不能因为 Jira 暂时失败丢失工作结果。MVP 暂不自动改变各项目 Jira Status，待状态映射逐项目验证后再开启。

VSIX Views 的数据来源与时效

所有服务器状态都从 Workflow Service 读取，VSIX 不分别从 Jira/GitHub 重建另一份工作流。首次打开加载带版本的 Snapshot；之后优先通过 SSE/WebSocket 接收事件，失败时使用窗口重新聚焦刷新、手工刷新和 15–30 秒 Polling。每个 View 必须显示 lastUpdatedAt、Data Version、Source Health 和 LIVE/DELAYED/STALE/OFFLINE，缓存不得伪装成实时数据。

Scrum Master 的 Copilot 结果

SM 点击 Analyze Epic Risk、Prepare Stand-up、Find Blockers、Check Release Readiness 或 Draft Jira Update 时，VSIX 只在 Workflow Service 创建一个 READY AI Task，并打开/准备 Copilot 命令。只有 SM 手动运行 Delivery Coordinator Agent 且通过 Workflow MCP 提交后，才会保存版本化的 EPIC_RISK_REPORT、STANDUP_REPORT、BLOCKER_ANALYSIS、RELEASE_READINESS_REPORT 或 JIRA_UPDATE_DRAFT，然后 Workflow Event 自动刷新 View。每个 AI Panel 显示运行状态、生成时间和使用的 Source Snapshot；Draft Jira Comment 必须再次人工确认发布。

5. 弱 Jira Ticket：Onboarding 与当前代码结合

原则：Onboarding 是地图，当前代码是事实证据，Jira/Figma 是新意图，人类决定新的业务规则。
质量评分找出角色、边界、异常、NFR 和验收缺口
缩小范围用 Journey/Repo Onboarding 找页面、仓库、API
定向读代码验证路由、Client、DTO、测试、Flag 和错误处理
苏格拉底提问只把代码回答不了的业务决策问给 BA/PO
双批准业务行为与技术解释分别批准
证据等级
等级含义能否直接进入正式需求
TEST_VERIFIED测试明确证明当前行为可作为 AS_IS 证据
CODE_VERIFIED当前 commit 的代码明确证明可作为 AS_IS 证据
DOC_STATEDJira/Confluence/ADR 声明需检查与代码是否一致
HUMAN_CONFIRMED授权角色确认的新决策可以
AI_INFERRED模型推断不可直接成为业务规则
UNRESOLVED仍未解决Critical 时阻止 Design，除非记录有期限例外

Onboarding 必须绑定 sourceCommit、证据文件、生成时间、最后验证时间和已知缺口。即使为 CURRENT，也要针对本 Ticket 涉及的文件重新验证。

不要求用户预先知道完整仓库清单

Journey Onboarding 从业务范围加至少一个 Anchor 开始：Jira、Confluence、Figma、页面/Screen、API 或已知仓库。Agent 再沿 Child Tickets、Routes、API Clients、OpenAPI、Service Config 和 HTTP Calls 扩展发现。每个相关渠道最终分类为 REPOSITORY_VERIFIED、AUTHORITATIVE_DOC_ONLY、NOT_APPLICABLE、KNOWN_GAP 或 UNRESOLVED。

原则：输入不必完整，但缺口披露必须完整。开户 Hybrid Journey 理想覆盖 Web、API、iOS/AOS WebView 容器、JS Bridge、统一 Header、Session、Toggle 和返回路径；缺少代码时不能标为 CODE_VERIFIED。

6. 可以手动跳过 Architect/Designer 阶段吗？

可以跳过重复交流，不可以跳过责任。如果用户已经与 Architect 或 Designer 讨论过，VSIX 提供 Use existing decision，将已有结论转换成可审计制品。

允许

填写会议/评论/Figma 证据、参与人、日期、结论、未决项；Agent 只做结构化整理，不重新访谈。

条件允许

低风险变更可由用户自我声明；策略必须明确低风险定义，并记录 SKIPPED_WITH_EVIDENCE。

不允许

用户仅凭“我觉得聊过了”绕过高风险架构、兼容性、安全、数据、Accessibility 或发布批准。

跳过表单必填项

  • 跳过类型：已有外部 Review、不适用、低风险自证、紧急例外；
  • 证据引用：Jira 评论、会议记录、ADR、批准的 Figma 版本；
  • 参与角色、决策摘要、未决问题、接受风险和有效期；
  • 用户确认声明、Policy 计算结果和需要时的独立批准人。
高风险规则：跳过“Agent 会议步骤”不等于批准。高风险工作仍要求命名审批记录；MVP AUDIT_ONLY 记录但不验证其 TL/PO 身份，后期 ENFORCED 才强制角色。

能否跳过 Design Agent 直接 Coding？

可以跳过 Design Agent 的执行，不能跳过设计责任。已有人工设计且满足最小 Design Contract 时记录 DESIGN_AGENT_SKIPPED；低风险测试、文档、内部重构或局部修复可经 Policy 记录 FAST_TRACK_TO_CODING。跨仓、API/Data Contract、数据库、安全/PII、Hybrid/Native 接口、兼容性、Flag、发布顺序或基础设施改动均为 DESIGN_REQUIRED。

Coding Agent 至少领取范围、仓库、API/数据变化、兼容性、风险、测试、Flag/发布、回滚、决策和证据；跳过操作记录操作者、理由、Policy 结果和需要时的独立批准人。

所有 Native 调用使用统一 Platform/App-Version Header。缺失、未知或旧版本必须落入兼容旧行为，不能因新版本上线而失败。

潜在 Breaking Change
  • 删除/改名 Endpoint 或字段，新增必填请求字段；
  • 类型、Nullability、默认值或业务语义变化；
  • 新增 Enum 值导致 Native exhaustive switch 崩溃；
  • Status、错误码、认证、分页、幂等、重试行为变化；
  • 旧 App 仍发送原来合法的 Payload，但服务端不再接受。

每个相关 Design/PR 必须有 API Compatibility Report、消费者/版本矩阵、契约测试、Feature Flag 生命周期、监控、回滚、Deprecated 时间和删除条件。OpenAPI Diff 只能覆盖结构，不能替代行为审查。

11. 自动测试、手工 E2E 与 Accessibility

Copilot 生成测试，Jenkins 执行测试；“AI 已生成”不等于“测试已通过”。测试报告统一展示验收标准 × 自动化 × 手工 E2E × Accessibility 覆盖矩阵。

自动化

Unit、component、integration、contract、UI/E2E、错误、重试、版本兼容和 Feature Flag 组合。

手工 E2E

WebView/Native 切换、真实设备、Session、Back Stack、弱网、升级/回滚和无法稳定自动化的路径。

Accessibility

Web WCAG 2.2 AA；iOS VoiceOver/Dynamic Type；Android TalkBack/字体与显示缩放。

测试和缺陷使用 a11y:web|ios|android、a11y:keyboard、a11y:screen-reader、wcag:<criterion>、test:auto|manual 和严重度标签。

测试定位标签（data-testid、iOS accessibility identifier、Compose test tag）不能代替用户真正依赖的 Accessible Name、Label、Role、Value 和 Semantics。

12. VSIX、Workflow API、Server MCP、Local MCP 日志

一条可关联的 Trace

traceId → workflowId → taskId → ticketId
        → repositoryId → commitSha → pullRequestId

身份与责任追溯

principalId 是 Workflow Service 为“一个人”创建的随机、不可变内部主键，不是 VSIX 安装 ID，也不表示该人已经 Onboard VSIX。目录导入可以提前创建 Person 和 principalId，再通过 identityLinks 关联可变化的工号、GitHub Enterprise Login、邮箱及未来 SSO Subject。用户第一次登录 VSIX 时只链接已有 Person，避免重复建人。

MVP 对实际登录者使用 GitHub Enterprise 登录 + 管理员确认工号绑定。未安装 VSIX 的人员仍可存在于目录并被预分配任务；他们在登录前不能执行本地 Copilot，任务显示 ASSIGNEE_NOT_ONBOARDED，由 SM 查看、通知或改派，而不阻塞其他子 Workflow。

权限模式为 AUDIT_ONLY：所有已登录用户都能创建、加入、启动、批准或跳过，但声明的 TL/SM/PO 等角色标记为 UNVERIFIED_ROLE；高风险和同人双批准只警告不阻止。以后接入公司 SSO/Teambook 后切换为 ENFORCED，不改变既有 Workflow 数据结构。

Pod Team 与任务路由

中央仓库只维护无个人信息、可 Review 的规则：podId、Journey/Domain Ownership、Repo Pattern、Jira Component/Label、能力与角色槽位。不把姓名、邮箱、工号或成员名单放进 Git，避免人员信息进入永久历史且频繁产生配置 PR。

MongoDB 保存 directoryPeople、identityLinks 和 teamMemberships。MVP 使用中央 importing-pod-members Skill：Agent 只通过 Workflow MCP 做 DRY_RUN → 脱敏 Preview → 明确确认 → APPLY → Import Report，不直连 Mongo/Jira。它可导入从未使用 VSIX 的人员；以后用 TeamDirectoryProvider 接入 Teambook。

每个决策、批准、跳过、指派和状态变化写入 Append-only Audit Event：principalId、工号、当时姓名/邮箱快照、身份来源、Actor Type、Initiator、时间、理由、证据、Agent/Skill/Bundle 版本和前后状态。Agent 结果同时归因给本地 Agent 定义和发起/提交它的人。

隐私与凭据：普通日志脱敏邮箱/工号，MVP 只向已认证公司用户开放并遵循保留策略，细粒度角色限制后置。Jira/GitHub Token 只存 SecretStorage/批准的凭据服务；Workflow Service 不信任 VSIX 发送的可编辑姓名文本。SSO 接入细节明确后再升级到企业 SSO。

Workflow Service 使用 ArtifactStore 抽象：MVP 的 MongoDocumentArtifactStore 保存权威结构化内容，JiraAttachmentPublisher 只投影可选的人类快照；GridFS/S3 后期再接。Jira 附件失败记录 JIRA_ARTIFACT_SYNC_PENDING/FAILED，不丢失 MongoDB 事实。没有批准的大附件存储时，视频/大型截图标记 LARGE_ARTIFACT_STORAGE_UNAVAILABLE。

只连接公司 MongoDB

公网实现不启动本地 Mongo，也不包含容器编排、Embedded Database、MinIO 或 Testcontainers。Java Workflow Service 只提供 application-mongodb.example.yml、环境变量占位、Index Manifest、Setup Notes 和 Connection/Health Diagnostics。Unit/Demo 使用 Fake Repository；内网 Agent 在批准的公司非生产 MongoDB 运行集成测试并提交脱敏报告。

长上下文不等于保存聊天。每一阶段输出结构化 Contract、人类可读 HTML 快照、Source Manifest、Decision/Open Questions 和 Handoff Summary；下一 Agent 只领取相关子图、报告摘要、证据链接和当前 commit。

关机后，VSIX 的 My Work 从 Workflow Service 恢复最后完成阶段、结果版本、批准状态和下一步。如果结果尚未提交，Lease 到期进入 RECOVERY_REQUIRED，展示最后显式 Checkpoint、Workspace/Branch/Commit Manifest，并允许继续或重跑；不能把中断误报为完成。

14. 还可以提高的地方

LLM Wiki（MVP 后）作为单独审批的知识层实验，不是 MVP 依赖。保留不可变原始资料、生成 Wiki、Schema/Index/Log、来源证据、ACL 过滤和过期标记；所有语义推理仍由用户在本地 Copilot 发起。
风险分级不要让小文案变更走完与高风险跨仓迁移相同的门禁；由 Policy 选择轻量、标准、增强流程。
配置分层组织基线 → Domain → Journey → Repo → Ticket。安全底线由 Policy 强制，不能只依赖 Instruction 优先级。
上下文预算每次记录加载了哪些文档、代码范围、Token/文件预算和遗漏风险，避免“长上下文”等于无选择地塞入全部资料。
兼容性工程增加 Consumer Contract、App 版本采用率、Release Train 日历、Feature Flag 到期治理和旧行为删除条件。
知识新鲜度制品依赖图自动标记 POSSIBLY_STALE，但仍由用户启动 Copilot 执行语义刷新。
Eval 驱动中央 Agent/Skill/Instruction 变更必须经过格式、安全、行为和历史案例回归，再 Canary 给少量用户。
可恢复性支持阶段重放、部分重试、跨仓子任务失败隔离、孤儿任务和人员离职后的 Owner 修复。
反馈闭环从脱敏失败、跳过原因和 Review 漏洞中生成新的 Eval Case；禁止把原始公司数据复制进公网。

新能力通过版本化扩展点加入，不修改一个巨型 Agent：Instructions、Skill、Agent、Hook、Schema、Policy、Eval 和 MCP Catalog 各自独立演进。

16. 验收标准

  1. 用户从 VSIX 中的 Jira Ticket 开始，并清楚看到下一 Agent、Skill、输入、输出和状态。
  2. 所有 AI 推理只发生在本地 Copilot Chat；服务器与 Jenkins 无模型。
  3. 弱 Ticket 能结合 Onboarding 和当前代码生成有证据的 Requirement Contract。
  4. 业务和技术采用双批准；已有会谈可审计跳过，但高风险责任不可自我消失。
  5. Journey 图能追踪页面/Screen → API → Payload → Response → 下一跳。
  6. 开户 Journey 使用 App 内 WebView；其他 Journey 逐个确认。
  7. Web/API 先行和 Native Release Train 通过统一 Header、AWS Toggle、兼容矩阵和回滚保护。
  8. 规范能按 Instructions/Skill/Agent/Hook/Schema/Policy/Eval 正确扩展。
  9. VSIX、API、Server MCP、Local MCP 可通过相关 ID 在 Splunk/本地日志中联合诊断。
  10. 自动化、手工 E2E 和 Accessibility 证据都能映射到验收标准。
  11. 多 Ticket 交付由一个 Epic 父工作流、技术栈 Ticket 子工作流和内部 Repo Delivery Task 组成，不重复共享需求分析。
  12. Jira 获得简洁且幂等的里程碑评论；Workflow Service 保留权威、可恢复的完整审计记录。
  13. GitHub Enterprise 身份和管理员工号绑定能把每次决策、跳过和状态变化关联到验证主体。
  14. Scrum Master 在 VSIX 中查看依赖、Blocker、Owner、批准、PR/CI、发布、Toggle 和 QA，并手动运行本地 Delivery Coordinator Agent。
  15. 所有 VSIX View 显示更新时间、数据版本、来源健康和 Stale/Offline 状态，并支持事件推送、Polling 和手工刷新。
  16. Epic 可在部分 Onboarding 下开始；高风险 Design/Coding 前关键渠道需验证证据或已记录的 Known Gap 风险接受。
  17. 中央 Git 只保存无个人信息的 Pod 路由规则；MongoDB 保存成员映射和任务分配，后期再接 Teambook。
  18. MVP 权威制品使用结构化 MongoDB 和按需 HTML；Jira 保存摘要/可选附件，GridFS/S3 不是依赖。
  19. 目录导入可在用户安装 VSIX 前创建 principalId 和 Pod Membership；首次登录只链接身份。
  20. My Work 是开发者首页，Ticket Detail 是交付聚合，Repo Task Detail 是嵌套的代码级 Drill-down，不形成重复顶层 View。
  21. 中央源码仓库和 Release Bundle 明确包含 Agents、Skills、Instructions、Hooks、MCP、Schemas、Policies、Templates、Evals、Onboarding/Routing、Manifest 和 Versions。
  22. 公网实现没有本地 Mongo 启动、容器编排、Embedded Database、MinIO 或 Testcontainers 依赖。
  23. Pod 导入 Skill 强制 Workflow MCP Dry Run、脱敏 Preview、明确确认、幂等 Apply 和 Import Report。
设计基线状态：本报告可进入内网能力验证和实施计划更新；真实 AWS Toggle、Header 名称、认证和各仓库框架仍需要内网 Agent 输出报告确认。
