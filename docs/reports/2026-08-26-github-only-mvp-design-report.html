GitHub-only multi-Agent SDLC

A practical workflow for teams that can only use local VS Code GitHub Copilot Agent: shared long-lived context lives in Git, people review it in one Journey PR, and every AI action is manually started by a person.

Git is the source of truthLocal Copilot onlyThree workflowsVSIX optionalNo server-side Agent

Decision at a glance

Keep

One Journey repository

It holds workflow state, approved Markdown reports, Context Receipts and links to code PRs. It does not copy application source code.

Keep

One active Journey PR

The shared human report workbench for BA, architect, QA, developer and scrum master. Code repositories retain their own code PRs.

Defer

Workflow Service / Mongo / MCP

They improve scale later, but are not needed to prove the pilot. Local MCPs are optional connectors, not persistence.

The three workflows

01 · prerequisite

Onboarding / Sync

Build and refresh reusable Journey context: repositories, call graph, entry points, contracts and known gaps.

Owner: code-context-analyst

02 · coordination

Journey / Epic Delivery

Turn an Epic or urgent change into a scope, delivery DAG, cross-channel plan, compatibility plan and ticket matrix.

Entry: delivery-coordinator

Requirements, design, plan, code evidence, test evidence and review for a channel ticket under the Epic.

Required onboarding outputs

  • Journey baseline and repository landscape

Single technical ownership

Only code-context-analyst derives cross-repository HTTP/API relationships. epic-delivery-analyst consumes the approved graph for delivery planning; it must block rather than invent a call edge.

Every output begins PENDING_APPROVAL. The human approves it in the Journey PR, requests changes, or records an attributed SKIPPED_WITH_EVIDENCE decision. The coordinator persists that decision through record-human-decision with actor/evidence/timestamp (plus reason and accepted risk for a skip), then advances one declared stage only; missing, stale, blocked or unapproved context stops the route.

Journey PR: the shared report workbench

After every Agent report

  1. Validate the Markdown and receipt.
  2. Commit only the Agent's report, receipt and workflow metadata.
  3. Create/update the one Journey PR.
  4. Upsert its marked report comment with the decision needed and the next prompt.
  5. Keep the result PENDING_APPROVAL until a human acts.

What people see

  • Canonical report links and rendered Markdown
  • Tables, diffs and native Mermaid where GHES supports it
  • Approval/change/skip decision requested
  • Recommended next Agent and /resume-workflow prompt
  • Links to associated API/Web/iOS/Android code PRs

GitHub PR comments should not depend on arbitrary HTML, CSS or JavaScript. Large reports remain committed Markdown and are linked from the marked comment.

Optional VSIX: useful, not authoritative

What it does

Renders the checked-out reports as structured local HTML, shows current stage/receipt freshness/PR links, recommends the next Agent and refreshes when artifacts or workflow state change.

What it never does in MVP

It does not call a model, receive a webhook, become a server, store the canonical workflow, approve a report or advance a stage. The Journey PR is the shared team interface.

Integration, logging and security boundary

Local integrations

Jira, Confluence, GitHub Enterprise, Figma and future code-graph tools can be connected through local MCPs started on the user's intranet machine. gh or VS Code source control is the local publishing fallback.

Audit and safety

Git commits, pull requests and CI checks form the durable audit log. Keep local VSIX diagnostic logs. Do not log tokens, credentials, sensitive source/data, raw prompts or hidden model reasoning.

Jenkins/GitHub CI may run deterministic builds, tests and receipt validation. It is not an AI Agent. Internal connectivity and permissions must be validated by an intranet Agent using a redacted report, never by uploading company source code.

First pilot: the human path

1 Install the central Copilot customization package and clone/select the private Journey repository.

2 Start code-context-analyst to run Journey onboarding. Review and merge the baseline PR.

3 Start delivery-coordinator and enter /start-epic <id>. It validates onboarding before it creates the Journey change branch.

4 For each ticket, start requirement-analyst; approve its Journey PR output, then use the coordinator to route the next specialist.

5 At any interruption, pull the branch and use delivery-coordinator with /resume-workflow <workflowId>.

Success criteria and deliberate future work

Pilot is successful when

  • Start Epic blocks reliably on stale/missing onboarding.
  • Every stage has a fresh Context Receipt.
  • All outputs are discoverable in one Journey PR.
  • State is recoverable from Git without chat history.
  • QA output clearly separates proposed and executed evidence.

Revisit after evidence, not before

  • Workflow Service, MongoDB and Workflow MCP
  • LLM Wiki / knowledge retrieval
  • S3 storage, graph aggregation and automatic Jira projection
  • SSO, Teambook pod/role sync and fine-grained permissions
  • Central Scrum board, webhooks and cloud MCPs
